# AGENTS.md

NSH lab: an app for trying Native Shell (NSH) features by hand. A sidebar of feature groups that expand and
collapse; the selected feature's page renders in the middle. Pages show what a feature does, with live examples,
and for changed behavior the result now beside the result before.

It lives outside the NSH repository and its worktrees on purpose: it never
goes into an NSH commit or PR. It depends on no NSH checkout: **the `nsh` binary that runs it decides which NSH is
tested**. Use the `target/debug/nsh` of the checkout or worktree whose changes you want to see, by its full path
(never a bare `nsh`, which is whatever is on `PATH`, usually an older build in `~/.cargo/bin`).

## Commands

```sh
NSH=<checkout or worktree>/target/debug/nsh                     # built there with `cargo build -p nsh-cli`
$NSH run . --target macos --window-size 1440x900                # a centered macOS window, hot reload on save
$NSH run . --target web                                         # also ios, android, linux, windows, gpui
$NSH check .                                                    # type check
$NSH test .                                                     # src/App.test.tsx, headless: every page opens, groups collapse
echo 'await app.wait(500); await app.press("id:nav-svg"); await app.wait(400); await app.screenshot("/tmp/svg.png")' \
  | $NSH test App.tsx --target macos                            # a screenshot of a page in a real window
```

`nsh test --target macos` opens a phone-sized window (390×844); screenshots there are narrow, which is the test
window, not the app. Wait a moment before the first press: a press before the app has loaded is lost.

## Layout

```
App.tsx             the entry `nsh` runs (it looks for `App.tsx` next to `nsh.json`): one line importing src/App.tsx
src/App.tsx         the shell: `groups` (the sidebar's content), the sidebar, the page area; the window's title
src/ui.tsx          the building blocks every page uses (below)
src/pages/*.tsx     one page per feature, exporting one component named like the file
src/App.test.tsx    opens every page by its sidebar id; checks a group collapses and expands
assets/             images the pages import (`../../assets/…` from a page; see "Assets")
README.md           how a person starts and checks the app
nsh.json            the app's name and id
```

All sources go under `src/`; the root keeps only the entry, the configuration, the docs and `assets/`. `.nsh/` is
generated by `nsh` (types, build output) and ignored.

### Where a new file goes

| New file | Place | Notes |
|---|---|---|
| A feature's page | `src/pages/<Feature>.tsx` | PascalCase, named like its component (`Sticky.tsx` exports `Sticky`); one page per file |
| Helpers only one page uses (data, a small component) | in that page's file | move them out only when a second page needs them |
| A building block several pages use | `src/ui.tsx` | with a doc comment saying what it is for |
| Larger shared code (several components, data, utilities) | `src/<area>/<name>.tsx` / `.ts` | e.g. `src/data/people.ts`; never at the root |
| A test | `src/<name>.test.tsx`, next to what it tests | `nsh test` finds `*.test.tsx` anywhere; open the app with `open("<relative path to the root App.tsx>")` |
| An image or other asset | `assets/` (the root) | imported from a page as `../../assets/<file>`; see "Assets" |
| A script that generates assets | `tools/` (the root) | not imported by the app; say in "Assets" what it makes |

Never add sources at the root: there `App.tsx` stays the one-line entry, beside `nsh.json`, `tsconfig.json`, the docs
and `assets/`.

## The sidebar: groups and features

The sidebar is the `groups` array in `src/App.tsx`: groups, each with its features. A group is an area of NSH
(`Tailwind`, `SVG`, `Images`, `Lists`); a feature is one page.

```ts
{ id: "images", title: "Images", features: [
  { id: "density", name: "Multi-resolution images", detail: "@1x / @2x / @3x siblings", page: Density },
] },
```

- **Group**: `id` short, lower case, unique (`group-<id>` is its header's test id); `title` the area as people name it,
  one or two words, title case (`Tailwind`, `SVG`, `Lists`). Add a feature to the group of the area it belongs to; make a
  new group only for an area none covers, and keep groups in the order of the sidebar's story: what is being worked on
  first, then the areas of earlier work.
- **Feature**: `id` short, lower case, unique across all groups (`nav-<id>` is its item's test id); `name` the
  feature as a heading (`Sticky list headers`, `Borders and outlines`); `detail` a few lower-case words naming what the
  page shows, the classes or props themselves where they fit (`border-none, outline styles`,
  `stickyHeaderOffset and fixes`); `page` the page component.
- A page about one class family can sit in the area it is about and still be a Tailwind page: `Images: object-fit` is
  under Tailwind because it is about the `object-*` classes. Name it with its area as a prefix then.
- Groups start expanded. Don't add state that hides features by default.
- Every new feature id goes into the list in `src/App.test.tsx`, with the page's exact title.

## Pages

A page is one feature, built from `src/ui.tsx`, in this shape (see `src/pages/Layout.tsx`, `src/pages/Svg.tsx`):

```tsx
export function Borders() {
  return (
    <Page
      title="Borders and outlines"
      intro="What the feature is and what changed, in two or three sentences: the classes or props by name, what they do now, and what NSH did before when that differs."
    >
      <Section title="border-none border-2" note="Optional: what to look at, or why it matters, in one or two sentences.">
        <Compare
          nowCode={`class="border-none border-2"`}
          now={<View class="size-16 border-none border-2" />}
          beforeCode={`border-none was width 0, so border-2 brought it back`}
          before={<View class="size-16 border-2" />}
        />
      </Section>
    </Page>
  );
}
```

- **`Page`** (`title`, `intro`): the title is the feature's `name` from the sidebar. The intro says what the feature is
  and does, then what changed, naming the classes / props / values; a reader who reads only the intro knows what the
  page is about.
- **`Section`** (`title`, optional `note`): one behavior per section. The title is the code it is about, as written
  (`leading-tight text-lg`, `` borderStyle: "none" ``, `-space-x-* (overlapping avatars)`) or a short heading for a
  broader point (`Sharp at any size`). The note says what to look at, what to do (`Tap the buttons`, `Scroll the
  list`, `Hover the card (desktop)`), or the platform it applies to.
- **`Compare`**: for behavior that changed. `now` is the feature as it works now, written exactly as an app would
  (`nowCode` is that code, verbatim); `before` reproduces what NSH drew before with styles or other classes, and
  `beforeCode` says how (the code, or what the old behavior was: `outline-2 forced solid`). Both panels get the same
  content and size, so only the difference shows. `nowLabel` / `beforeLabel` replace the labels when the pair compares
  something else (`LTR` / `RTL`); say so in a `Note`.
- **No `Compare`** for features that are new or unchanged (SVG, multi-resolution images, sticky headers): show the
  feature itself in several cases, from the simplest to the edge cases, with `Code` labels naming what each shows.
- **Interactive** where the feature responds to something: `Segmented` to switch sizes, modes or offsets, a button that
  toggles (see the `fixed` section), a counter for taps (see `src/pages/Inheritance.tsx`), selectable text. Prefer an
  example people can operate to a static one.
- **`Note`**: one-line remarks under an example: where to look, platform differences (`Run with --target web to see
  the fix`), what a class still does.
- **`Code`**: a class, prop or value in a monospace chip.
- Examples use `Chip` (a labeled square) and `Avatar` for things to move around, and `bg-zinc-100` stages for space to
  move in; reuse them before making new ones.
- Style pages with Tailwind classes, as the rest of the app is: plain zinc greys, one accent color per example
  (sky, violet, rose, amber, emerald), `rounded-*`, small text for notes. Keep it quiet: the examples are what people look at.
- Write in English, in full sentences, plainly: say what something is and does. Name NSH's behavior precisely (which
  class, which platform), and keep claims to what the page shows.

### Pages for unknown or platform-specific things

- A class NSH now refuses goes on the `Now unknown` page (`src/pages/Unknown.tsx`), with why. Unknown classes print
  warnings when the app runs; that page is the only one that uses them, so every other warning is a mistake to fix.
- Behavior that differs by platform says so in the section's note, and the page shows what the current platform does.

## Assets

Images go in `assets/` at the root and are imported from a page as `import badge from "../../assets/badge.svg"`. `name.png` with `name@2x.png` /
`name@3x.png` beside it ships as one multi-resolution image. The current files:

- `density.png`, `density@2x.png`, `density@3x.png`: 64×64 points; red 1x, green 2x, blue 3x, with a big `1x` / `2x` /
  `3x` and one-device-pixel stripes at the bottom (sharp stripes mean the right density loaded).
- `large.png` (600×400) and `small.png` (60×40): a scene for `object-fit` / `resizeMode` examples, larger and smaller
  than a frame.
- `badge.svg` (96×96: gradients, a stroked star, opacity), `landscape.svg` (viewBox 320×160: clip path, gradients),
  `glyph.svg` (16×16, four colors): multicolor SVG.

Generate new test images with a script (PNG through Python's standard library, SVG by hand) rather than copying
pictures from elsewhere; describe them here.

## Done means

1. `$NSH check .` passes and `$NSH test .` passes (with every new feature id in `src/App.test.tsx`).
2. The app runs without warnings beyond the `Now unknown` page's.
3. You looked at the new or changed page in a real window (`nsh test App.tsx --target macos` with a screenshot step),
   and what it shows matches what its intro and notes claim. If NSH's behavior differs from the page's claim, find out
   which is wrong: fix the page, or report the NSH bug.
4. README.md's page table lists the page.
5. Commits here are small and say what they add (`Add a page for sticky list headers`); this repository is the lab's
   own, never NSH's.
